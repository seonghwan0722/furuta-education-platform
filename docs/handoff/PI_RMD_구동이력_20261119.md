너는 MATLAB/Simulink, Raspberry Pi, SocketCAN을 다루는 제어 엔지니어야. 기존 Furuta 회전 역진자 프로젝트를 이어서 작업해줘. 한국어로 답하고, 파일과 로그를 먼저 확인한 뒤 작업해줘. 기존 블록 배치와 배선은 유지하고, 큰 변경은 별도 파일로 저장해줘.

## 환경
- Windows 프로젝트 C:\Capstone1, MATLAB R2026b, Simulink, Raspberry Pi Blockset
- Raspberry Pi 5, Raspberry Pi OS 64비트, can0 = MCP2515(8 MHz 클럭), Real, Classical CAN, 1 Mbps
- RMD-X6-P20-60-E (48 V, Kt 약 2.1 N·m/A, 출력축 기준), AS5600 펜듈럼 엔코더 (I²C 1, 0x36)
- RMD 요청 ID 0x141, 응답 ID 0x241. 0x92 각도 조회, 0xA1 전류 지령(0.01 A/count), 0x80 Motor Off, 0xA2 속도 지령

## 안전 제약
- 실제 모터 명령 시험은 내가 직접 시작한다. 너는 조회, 코드 생성, 빌드, 로그 분석까지만.
- speed_kp, max_target_rpm, 전류 한계·방향, watchdog 검증값은 실측 근거 없이 임의로 확정하지 마.
- 원인 추정 시 CAN 송수신 / 센서 유효 / 구동 잠금(인터록) / 실제 전류 응답을 구분해.
- 결과마다 PC 시뮬레이션, 코드 생성, Pi 실물 실행 중 어디까지 확인했는지 명시해.

## 주요 파일
- matlab_furuta/build_furuta_pi_hardware.m : Pi 모델 생성기 (ManualCurrent, SpeedControl, DriveProfile, AutoArmHome 옵션)
- matlab_furuta/furuta_pi_decode.m : 0x92 + AS5600 디코더 (자동 홈 포함)
- matlab_furuta/furuta_pi_frame.m : 구동 인터록과 0xA1/0x80 프레임
- matlab_furuta/furuta_pi_motor_output_drive.slx : 전류 수동 구동 모델 (현재 실물 시험에 사용 중)
- matlab_furuta/furuta_pi_motor_speed.slx : RPM 입력 모델 (구동 잠금 기본본)
- deployment/pi/rmd_x6_48v.json : 장치 프로필 (생성기가 CAN·센서 보정값을 여기서 읽음)
- deployment/pi/rmd_speed_drive_candidate.json : 구동 후보 프로필
- runs/pi_current_01~06.mat : 실물 실행 SDI 로그 (Simulink.sdi.Run.getLatest.export 결과)

## 지금까지 해결한 것
1. **can0이 500 kbps로 바뀌던 문제**
   - 생성된 Pi 앱은 시작할 때 `sudo ip link set can0 up type can bitrate <CAN.BusSpeed0>`를 실행해 can0을 재설정한다 (toolbox/rpib/raspiSL/src/MW_SocketCAN_raspi.c).
   - HardwareBoard를 'Raspberry Pi' → 'Raspberry Pi (64bit)'로 바꾸면 CAN.BusSpeed0가 500으로 리셋된다 (배치 시험으로 재현).
   - Simulink가 설정 변경 후에도 이전 빌드를 재사용한 적이 있다 → *_ert_rtw 폴더, .elf, .slxc 삭제 후 재빌드로 해결.
   - 생성기 수정: 모든 모드를 64bit 보드로 만든 뒤 프로필 bitrate(1 Mbps)를 쓰고 assert.
   - 확인 습관: 빌드 후 `*_ert_rtw/*.mk`에서 `MW_SOCKETCAN_IF_SPEED0=1000000`, Pi에서 `ip -details link show can0`가 1000000 / ERROR-ACTIVE.
   - 주의: furuta_pi_hardware.slx, furuta_pi_hardware_verify.slx와 기존 .elf는 아직 500 kbps 빌드다 (재생성 안 함).
2. **암 홈 불일치**
   - 0x92 원시각이 +73.65°로, 프로필 홈 −209.05°와 맞지 않아 암 각도 한계(±π)에 즉시 걸렸다 (candump 응답 `92 00 00 00 C5 1C 00 00`).
   - rmd_x6_48v.json의 arm_home_deg를 73.65로 변경 (백업 rmd_x6_48v.backup_20261119.json, arm_home_history 기록).
   - 자동 홈 추가: calibration(1)=NaN이면 furuta_pi_decode가 실행마다 첫 유효 0x92 각도를 홈으로 래치. 생성기 AutoArmHome=true가 기본 (검증 모델은 고정 홈 유지). 암 한계는 실행 시작 자세 기준.
3. **CAN 경로 검증**: candump에서 0x141 요청과 0x241 응답이 약 0.13 ms 간격으로 1:1 짝을 이루고, 5 ms 슬롯이 정상임을 확인.

## 남은 일
1. watchdog 시험: 회전 중 Pi에서 `sudo pkill -9 -f furuta_pi_motor_output_drive` → 약 100 ms 안에 토크가 풀리는지 (다른 CAN 송신은 모두 중지).
2. RPM 제어 방식 결정: PC 모의와 실측상 0xA1 전류 기반 P 속도 제어는 정지마찰(0.3 A)과 0.01 A 분해능 때문에 저RPM에서 정지↔급가속을 반복할 가능성이 크다. RMD 내부 속도 루프를 쓰는 0xA2 속도 지령 모델을 별도 파일로 만드는 안을 제안한 상태 (기존 인터록·Scope·자동 홈 재사용). 이 결정부터 진행해줘.
3. 결정한 방식으로 RPM 구동 모델 생성 → PC 모의 → 코드 생성 → 내가 실물 실행 → 로그 분석.
